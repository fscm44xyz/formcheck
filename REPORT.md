# formcheck at scale — M0 to M3

`formcheck` asks the question a gold check cannot: does a task's reward reject a
*correct* solution written differently? It answers it by transforming the
reference solution in ways that preserve behaviour and re-running the graded
tests. A transform that keeps the task's stated contract and still scores 0.0 is
a witness that the reward is coupled to the incidental form of the gold patch.

This report covers the scale work: running that check inside each task's own
epoch-pinned image, on verifiers' own runtime, over SWE-bench Verified.

---

## 1. The result that matters most is a defect, not a percentage

Five defects found in this work share one shape:

> **A check that reports success for a reason invisible in its own output.**

That is the exact failure `formcheck` was built to detect in other people's
graders. It kept appearing in `formcheck`. Every one was found by inspecting the
machinery, never by a suspicious number — because none of them produced a
suspicious number. That is what makes them the class they are.

| # | what reported success | what was actually true |
|---|---|---|
| 13 | `CLEAN`/`INVALID` verdicts | the P2P coupling partition had been silently reintroduced as collapsed, turning the project's most novel finding into an "invalid transform" count |
| D2 (16) | `CLEAN reward 1.0` | the graded memo answered from a digest that could collapse, serving the *control's* grading for a tree it never graded |
| 17 | `IDENTICAL` on the M0 gate | the gate's own reference file was regenerated by the test suite that ran against it |
| 18 | `INVALID` on four tasks | the failure attribution understood one test runner; those were coupling, i.e. **witnesses** |
| 19 | `7/7 passed` | six tests appended below a module-level collector were never run — including the ones pinning #18 |
| 21 | every guard green | the run had burned 330 tasks in 32 minutes against a refusing registry; the disk budget passed because nothing was pulled, the control passed vacuously because it never ran |
| 22 | `remaining: 100` | the governor probed the pull quota while the block was on token issuance — a measurement that looks right and means nothing, in the code written to prevent #21 |
| **23** | **nothing at all** | **two individually correct guards cancelled at their seam; the liveness check was silently disabled by the refusal-handling it was written to complement** |

### #23, because it is the strongest of them

Two requirements, both correct: *an infrastructure refusal is not a task result*,
and *assert something causally necessary — a real task cannot be fast*. The
first was implemented as an early `return`; it sat before the line feeding the
second. The refusal path skipped the liveness check entirely, and 107 tasks were
cycled in 41 seconds with nothing watching.

It is worse than the other seven for three reasons:

- **Correctness of parts does not compose.** No review of either requirement
  alone would have caught it. Each is right. The defect exists only at a seam
  neither owns.
- **A safety mechanism was silently disabled by another safety mechanism**, with
  no warning, no degraded mode, no event.
- **It was found by a human noticing that an event was absent.** Nothing in the
  machinery can observe its own silence.

It was also nearly recorded backwards. From a dead process and a frozen log the
natural reading was that the invariant had fired on a cause it was not written
for. It had not — zero `burn pattern` events, no `BurnDetected`, the run ends
mid-queue because a human killed it. Writing that down would have entered a
guard's success into the record on the strength of a clean-looking outcome whose
cause nobody asked about: this project's own failure mode, committed about this
project's own safety mechanism.

**The general rule, which outlives the incident:**

> A guard that has never fired in production is indistinguishable from a guard
> that cannot fire.

Both present as silence. Every invariant therefore needs a test proving it is
*capable* of firing, run alongside the rest — and guards must be extracted into
callable functions for that to be possible, since one inlined in a loop cannot
be driven to its raise. A test that checks only the predicate proves arithmetic,
not that anything happens.

### #18 in detail, because it inverted the headline

`failure_sections` parsed pytest's per-test failure blocks (`______ test_name
______`) and nothing else. Phase 4 ran only pytest repos, so that was sufficient
and looked complete. M3 ran ten repos and found two more shapes:

- **pytest collection errors** — one `______ ERROR collecting <file> ______`
  block for a module that failed to import. This is *precisely* what an
  alpha-rename produces when a test imports the renamed symbol by name: there
  are no per-test blocks at all.
- **unittest / django** — `====`, then `ERROR: name (mod.Class)`, then `----`,
  then a traceback. No underscore rules anywhere, so the parser found nothing.
  A module that will not import is reported as a synthetic
  `test_cookie (unittest.loader._FailedTest)`, naming the **module** and never
  the tests that were wanted.

Every failure in those logs came back "no failure section found" → unexplained →
the oracle concluded the transform broke behaviour → `INVALID`. All four such
rows in M3 name their symbol:

```
astropy-12907   ImportError: cannot import name '_cstack' from 'astropy.modeling.separable'
django-13195    ImportError: cannot import name 'CookieStorage'
django-15572    AttributeError: module 'django.template.autoreload' has no attribute 'get_template_directories'
pylint-4604     AttributeError: module 'pylint.checkers.variables' has no attribute 'VariablesChecker'
```

An alpha-rename changes no expression's value. A test that fails on those
messages is asserting the *name*. All four are witnesses.

**What would have been reported had it not been found.** `W = 0` witnesses over
50 tasks, with 50/50 controls passing, zero errors, zero aborts, zero disk
anomalies, and a 46-minute clean run. Under this project's own pre-committed
stopping rule that is the "M4 is optional, the deliverable is no longer the
number" branch. And `0/50` is exactly what a reasonable person expects from a
curated, heavily-reviewed benchmark — the number would have confirmed a prior,
which is the worst property a wrong number can have.

**What generalises past this project.** Attribution logic tested against one test
runner is untested logic, and its failure mode is *silent under-reporting*. It
does not crash, it does not warn, and it produces a plausible verdict. Any tool
that reads test output to decide why something failed inherits this: the parser
must understand every runner in the corpus, and a log it cannot parse must be
reported as unparsed rather than resolved to the nearest available verdict.

### How #18 is closed rather than patched

Teaching the parser three shapes is not closing it — a fourth shape would take
the identical path. So "cannot parse" is now separated from "genuinely broke":

| classification | meaning | verdict |
|---|---|---|
| `coupled` | a failure block that **names** the symbol | coupling |
| `broke` | a failure block that does **not** name it | `INVALID` |
| `unparsed` | **no failure block at all** | `UNVALIDATED` — unjudgeable |

An unparsed failure makes the oracle return `None`, which the hook renders
`UNVALIDATED` with a reason naming the test and calling it an unknown log shape.
It does not increment `judged`, so an unreadable log cannot enter a denominator.
`aggregate` reports `unparsed_log_shapes` as a number with the offending tasks
named and prints a `!!` line when it is non-zero. #18 was invisible because
unattributable failures had nowhere to surface except as `INVALID` verdicts that
looked like findings; now they have somewhere, and it is loud.

Tests pin all three known shapes, the unknown-fourth-shape contract, that the
oracle declines to judge it, and — so the partition cannot degrade into "we can
never tell" — that genuine breakage is still `INVALID`.

## 2. What was actually established

**The check runs on the real path.** `Task.formcheck` executes through verifiers'
own `_run_check(task, cfg, "formcheck")`, on `DockerRuntime`, with the image
resolved through `resolve_runtime_config` from `task.data.image` — the same call
by which a Harbor task reaches its container. What remains not-real is the
taskset, still a local stand-in, because no SWE-bench taskset lives in
`verifiers` any more.

**The container reproduces the July rig, field for field.** M0 gated
`pytest-10356` on operator, anchor, verdict *and refusal reason string*, and it
matched — including the `MarkDecorator` refusal that `writeup.md` §3.2 records as
having once landed on the right verdict for the wrong reason. That gate was
re-run after every subsequent change to the hook and has never moved.

**Reference solutions reproduce their own scores inside their own images.** This
is `writeup.md` §7's finding turned from an argument into a measurement, and it
is the most robust result here. Across four different test runners — pytest,
django's `runtests.py`, sympy's `bin/test`, sphinx's `tox` — controls passed
everywhere they were run. Two tasks the July rig could not check at all
(`pytest-7571`, "needs pytest 6.0, which cannot run on Python 3.11";
`pylint-6903`, "stalled at P2P 4/8 after three era-pins") reached a valid control
in-container on the first attempt with no pins.

**Coverage is bounded by anchor availability, not by refusals or oracle
strength.** Measured across 50 tasks: `symbol_rename` finds an in-scope anchor on
every one; `kwonly_specialize`, `collection_reverse` and `message_reword` find
one on none. That is a sharper version of `writeup.md` §6.5's ceiling.

## 3. Scope of the sample, decided in advance

Eligibility was measured from the gold patches with no container running:

| | |
|---|---|
| gold patches touching exactly one file | **429/500 = 85.8%** |
| gold patches with ≥1 production `.py` | 500/500 = 100% |

Production `.py` files per gold patch: 1→430, 2→48, 3→12, 4→7, 5→1, 6→1, 21→1.

SWE-bench Verified is overwhelmingly single-file. An earlier draft of this work
nearly asserted the opposite from memory; it was dropped unmeasured and this
replaced it.

**Multi-file tasks were included**, sampled as their own stratum and reported
separately, decided before the run: the widening had been exercised on a real
21-target task, and the M0 gate proves the single-target path collapses to the
pre-widening behaviour exactly.

The 50 ids were stratified by target-count group and then by repo, drawn at a
fixed seed, and **committed before any container started** (`664a3ab`). The
commit order is the evidence; a seed alone would not be, since a seed can be
tried repeatedly.

One design change is on the record: the first draw stratified by repo only and
returned zero multi-file tasks at p ≈ 0.0006. The draw was **re-designed, not
re-seeded** — the seed is unchanged — because a report specified to give two
groups separately cannot use a design that can return an empty group. Nothing
about outcomes had been observed; only the sample's composition, which is what
stratification exists to control.

## 4. Method notes that bound what the numbers can claim

**THE NUMBER is `symbol_rename`-only, and that is structural.** `symbol_rename`
is the only operator whose failure mode is LOUD — an incomplete alpha-rename
raises `AttributeError`/`ImportError`/`NameError` *naming the symbol*, so the
task's own PASS_TO_PASS suite is a sufficient oracle. Every other operator fails
silently, so on a task with no hand-written contract oracle its cases are
`UNVALIDATED`. Operators are never merged into one percentage, and that is
enforced rather than conventional: `witness_rate` has no operator-less arity and
the serializer refuses a report containing a rate that does not name its
operator.

**The denominator excludes tasks whose control failed.** A task whose reference
solution does not score 1.0 in its own image proves nothing in either direction,
and counting it as "no witness found" would convert a broken harness into
evidence of a clean reward.

**The anchor set is narrower than Phase 2's.** Applied mechanically, the rule
`writeup.md` §3.3 states yields `{get_unpacked_marks, store_mark}` on
`pytest-10356`; Phase 2 used a hand-picked set that also contained
`normalize_mark_list` and `MarkDecorator`, neither of which the gold patch
touches. The rule was **not** widened to recover them: widening until
known-interesting rows return is selecting for the outcome. `scale/SCOPE.md` sets
both rules out row by row, because a circulating demo shows the `MarkDecorator`
refusal and the current code does not produce it.

## 5. M3 — 50 tasks, measured twice

The sample: 50 tasks from `scale/ids_50.txt`, frozen and committed in `664a3ab`
before any container started.

**Run once with the broken attribution, then again with it fixed.** The original
records are kept as raw evidence; nothing was patched in place.

| | as run | re-run |
|---|---|---|
| controls passed | 50/50 | 50/50 |
| errors / aborts / digest anomalies | 0 / 0 / 0 | 0 / 0 / 0 |
| wall clock (3 workers) | 2743s | 3075s |
| **witness tasks (W)** | **0** | **4** |

**Exactly four rows differ between the runs**, all `INVALID -> WITNESS`, and 211
of 215 rows are identical:

```
astropy__astropy-12907     symbol_rename  _cstack                   INVALID -> WITNESS
django__django-13195       symbol_rename  CookieStorage             INVALID -> WITNESS
django__django-15572       symbol_rename  get_template_directories  INVALID -> WITNESS
pylint-dev__pylint-4604    symbol_rename  VariablesChecker          INVALID -> WITNESS
```

The measured re-run reproduces the offline re-classification exactly, to every
digit. That was worth doing anyway: a recomputation is sound, but it is not a
run.

### The numbers

**THE NUMBER — `symbol_rename` only:** 4 of 13 judged tasks, **30.8%**,
Wilson 95% **[12.7%, 57.6%]**.

| sampling stratum | tasks | witness / judged | rate | Wilson 95% |
|---|---|---|---|---|
| single-file | 43 | 2 / 10 | 20.0% | [5.7%, 51.0%] |
| multi-file | 7 | 2 / 3 | 66.7% | [20.8%, 93.8%] |

Reported separately and never blended, as specified before the run. At these
denominators neither stratum's rate is separable from the other; the intervals
overlap across almost their whole range.

**Per operator, by count — never merged into a percentage:**

```
symbol_rename        WITNESS=4  CLEAN=9  REFUSED=52
kwonly_specialize    NOT_APPLICABLE=50
collection_reverse   NOT_APPLICABLE=50
message_reword       NOT_APPLICABLE=50
```

**Anchor availability — the coverage ceiling:** `symbol_rename` 50/50 = 100%;
the other three operators **0/50 = 0%**. This is the sharpest form of
`writeup.md` §6.5's finding: coverage is bounded by anchor availability, not by
refusals and not by oracle strength. Three of four operators found no in-scope
anchor on any of fifty tasks.

**Witness split:** `f2p_only` 1, `p2p_coupling` 3, `p2p_unattributed` 0. Three of
four witnesses are the `writeup.md` §6.2 class — coupling located in
PASS_TO_PASS, the part of a task meant to be stable background, which a detector
inspecting only the graded test would miss entirely.

**Loud/silent:** all 13 judged cases and all 4 witnesses are `symbol_rename`, the
only LOUD operator. Zero judged cases from the three silent operators. This is
why THE NUMBER is `symbol_rename`-only.

**Controls:** 50/50, across django's `runtests.py` (23 tasks), pytest (15), tox
(4) and sympy's `bin/test` (8). No control failures, so the new triage fields
have nothing to report — which is itself the reproducibility result.

**`on_prime_hub`:** resolved 0/50. Null by design and never guessed; deciding it
needs a hub environment index that nothing in this repo, `verifiers` or
`swebench` can reach offline.

**`unparsed_log_shapes`:** 0 rows across all 50 tasks.

### D2 digest pairs, on the record

The six `CLEAN` rows produced before the digest fix, re-verified in-container.
The discriminating evidence is not the verdict — `CLEAN` is what *both*
hypotheses predict — but whether the transformed tree's digest differs from the
control's. A match would be D2 firing whatever the row said.

| task | anchor | verdict | control digest | transformed digest | differ |
|---|---|---|---|---|---|
| `pytest-7571` | `LogCaptureFixture` | CLEAN | `5f2e7531f04c7299` | `5d309b360b06140b` | yes |
| `scikit-learn-14894` | `BaseLibSVM` | CLEAN | `ccfc0a4185db88ba` | `b151bb2a1405578f` | yes |
| `sphinx-9591` | `PyProperty` | CLEAN | `40db87919b87bda2` | `397a6b386154453d` | yes |
| `sympy-13091` | `ModuleElement` | CLEAN | `d8954f8f08bf8861` | `9bb699145b752e61` | yes |
| `sympy-13091` | `QuotientRingElement` | CLEAN | `d8954f8f08bf8861` | `a6ee2a5eb0da029f` | yes |

Every judged row has a digest distinct from its control. Combined with M3's
50-task zero-anomaly result across ten repos — the corrected digest *raises* on
any failure — D2 is ruled out for every prior run, family-wide.

**One row moved during that re-verification, and it is the fourth shape
arriving.** `sympy-13091:FracField` went `CLEAN` -> `UNVALIDATED`: reward 0.0
with one failing test (`test_bug_sqrt`) whose failure block the attribution could
not parse, because sympy runs `bin/test` and emits neither pytest nor unittest
format. Under the closure described in §1 that is `UNVALIDATED` with the reason
naming the test and calling it an unknown log shape — loud, excluded from the
denominator, and not resolved to a verdict. It is a real coverage gap, and it is
reported as one rather than as a finding.

## 6. M4 budget, measured from M3

| | measured over M3's 50 | projected over 500 eligible |
|---|---|---|
| wall clock, 3 workers | 3075s | **~8.5 h** |
| wall clock, 5 workers (RAM-bound max) | — | **~5.1 h** |
| mean per-task worker time | 180s (min 35, max 1312) | — |
| image bytes pulled | 221.9 GiB (mean 4.44 GiB/task) | **~2.2 TiB transferred** |
| peak resident image store | 24.6 GiB at 3 workers | ~33 GiB at 4 workers |
| peak host RAM | 1.64 GiB (+0.63 over idle) | ~2.2 GiB at 4 workers |
| max per-task disk residual | 1.6 MiB | — |
| tasks leaking an image or container | 0 / 50 | — |

Against 947 GiB free and 9 GiB RAM, neither disk nor memory binds. **"A weekend
of compute" overestimates this by roughly an order of magnitude: M4 is a single
overnight run.** The binding cost is network — 2.2 TiB pulled and discarded —
which is why rotation removes each image immediately rather than caching.

M4 runs all 500 eligible tasks, including the 50 from M3, so the dataset is
uniform and M3's results are reproduced inside it as a consistency check.
